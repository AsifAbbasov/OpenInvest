## Purpose

Stage 3.7 defines the reviewed implementation boundary for atomic append of user-approved import
rows into the existing immutable ledger.

Stage 3.6 deliberately stopped at an append request plan. Stage 3.7 may only proceed after this
planning scope is reviewed and approved, because append changes financial history and must preserve
idempotency, deterministic snapshot rebuilds, auditability, and explicit user confirmation.

## Planning scope

This planning PR may only:

- document the Stage 3.7 implementation boundary;
- define allowed and forbidden implementation surfaces;
- define financial, privacy, security, and test expectations;
- define rollback and review requirements;
- synchronize governance registries.

No implementation is authorized by this planning document alone.

## Proposed Stage 3.7 implementation outcome

After a separately approved implementation PR, the system should be able to:

```text
CSV import review result
→ explicit user-approved append decisions
→ atomic append transaction
→ immutable ledger entries
→ snapshot rebuild
→ summary read
→ audit evidence
```

## Proposed allowed implementation

The future Stage 3.7 implementation PR may include only the minimum code required for:

- accepting an in-memory import append plan generated by the Stage 3.6 importer;
- validating explicit append decisions again at the application boundary;
- executing all approved append rows in one database transaction;
- rejecting the entire batch if any approved row is no longer valid;
- reusing the existing immutable transaction append and snapshot rebuild invariants;
- applying batch idempotency at the application boundary;
- recording minimal audit evidence for the append batch;
- unit and integration tests for success, rollback, duplicate, conflict, idempotency, and snapshot
  rebuild behavior.

## Forbidden in Stage 3.7 implementation

Stage 3.7 must not introduce:

- public import API endpoints; those require a separate future planning amendment or stage;
- frontend upload screens;
- raw broker-file persistence;
- SQL import-session tables unless this planning document is amended and approved first;
- direct broker API synchronization;
- credential scraping or broker login collection;
- external MOEX, CBR, Rosstat, broker, or provider integrations;
- XLSX or PDF parsing;
- background workers;
- automatic append without explicit user approval;
- mutation or deletion of existing ledger transactions;
- tax calculation;
- mobile implementation;
- AI assistance or interpretation.

## Financial and ledger rules

- Import append is append-only. Existing financial history must not be mutated.
- The batch must be atomic: either every approved row appends and snapshots rebuild, or nothing
  changes.
- Business dates remain SQL `DATE` semantics and must not depend on system timestamps.
- Decimal strings and existing Decimal/Money rules remain mandatory.
- Reversal, correction, or delete semantics are out of Stage 3.7 scope.
- Snapshot rebuilds must be deterministic from immutable ledger state.

## Idempotency and duplicate policy

- The implementation must reject repeated execution of the same approved append batch.
- Stage 3.6 row hashes and normalized fingerprints may be used as inputs, but Stage 3.7 must not
  rely on client-provided trust.
- Existing duplicate and conflict checks must run again before persistence.
- Duplicate decisions inside one append request must be rejected.

## Privacy and security rules

- No broker credentials are collected.
- Raw import files are not persisted.
- Spreadsheet-formula neutralization from Stage 3.6 must not be bypassed when review data is
  surfaced.
- Imported data remains private portfolio data and must not enter CDN/public cache.
- Audit records must not contain raw file content, secrets, passport data, INN, or tokens.

## Test expectations

The future implementation PR must include tests for:

- successful atomic append of multiple approved rows;
- rollback when one row fails validation;
- idempotent retry of the same batch;
- duplicate decision rejection;
- conflict row rejection;
- snapshot rebuild after append;
- audit evidence creation;
- no raw file persistence;
- no provider integration or worker activation.
