## 1. Problem

OpenInvest Web remained pinned to Next.js `16.3.2`, while the maintained 16.x line released
`16.3.3` with fixes for two Critical upstream advisories. The dependency version therefore remained
inside the affected ranges until this candidate.

## 2. Root cause

The project intentionally uses an exact framework pin. Exact pinning avoids silent framework drift but
makes security maintenance an explicit governed operation. The patched upstream version appeared after
the prior dependency baseline was frozen.

## 3. Failure / attack scenarios

### 3.1 Windows-hosted-server advisory

Upstream marks `>=16.0 <16.3.3` as affected. Repository evidence does not demonstrate Windows
production hosting, so dependency applicability is recorded without claiming proven OpenInvest
exploitability.

### 3.2 AVIF Image Optimization advisory

Upstream marks the affected 16.x range below `16.3.3`. Repository review found no current
`next/image` usage and no AVIF opt-in in `next.config.ts`; therefore an active OpenInvest path is
not asserted.

### 3.3 Maintenance stagnation

Keeping `16.3.2` indefinitely merely because project-specific exploitability is unproven would retain
a known-affected dependency and increase later emergency-response cost.

## 4. Impact

The original repository-audit severity remains P3. Upstream vulnerability severity is Critical, but
project-specific reachability was not demonstrated. The practical project risk is known affected-version
state plus future topology/configuration applicability and avoidable maintenance debt.

## 5. Chosen remediation

- `next 16.3.2 -> 16.3.3`;
- keep React/ReactDOM `19.2.7`;
- keep TypeScript, @types, Node policy and `pnpm@11.8.0`;
- let the real pnpm resolver regenerate Next.js-related lock identities;
- accept only the exact expected Next.js-family lockfile transformation;
- make no application-source or architecture changes.

## 6. Rejected / non-selected approaches

### Stay on 16.3.2

Rejected as a long-lived remediation because the installed version remains in the upstream affected
range.

### Move to a 16.4 canary for the cache-components memory report

Rejected. OpenInvest does not currently enable `cacheComponents` / `use cache`; applicability is not
evidenced and canary adoption would broaden risk.

### Bundle React maintenance

Rejected as unnecessary scope. React and ReactDOM `19.2.7` remain compatible with the target.

### Hand-author lockfile identities

Rejected. Runtime dependency state must be generated by the real resolver and verified against the
frozen expected transformation.

## 7. Local tooling forensic history

### Runner v1 — false drift result after failed preflight

**Cause:** a preflight helper treated the direct dependency line `specifier: 16.3.2` as a non-Next
occurrence.

**Secondary cause:** v1 lacked immediate shell termination after that helper error. Its expected oracle
was not created, but a later comparison still ran and emitted a misleading drift failure.

**Impact:** local-only execution anomaly. No commit, push, PR or protected-branch mutation occurred.

**Remediation:** v2 added fail-fast shell behavior and a structural comparator.

### Runner v2 — structural comparator false positive

The uploaded v2 evidence was reviewed before v3 was created.

**Observed raw result:** pnpm changed only the exact approved Next.js-family patch identities. No
unrelated transitive dependency changed. Resolver-generated package.json and lockfile from v1 and v2
were byte-identical.

**Cause:** v2 normalized snapshot package headers ending with `:`, but the pnpm snapshot for
`@next/env` is an inline empty mapping:

`'@next/env@16.3.2': {}`

The parser therefore normalized all SWC snapshot headers but missed that one `@next/env` line.

**Failure scenario:** the comparator reported semantic drift although the normalized-before and
normalized-after artifacts differed by only the missed `@next/env` patch-version line.

**Impact:** execution stopped safely; no repository mutation was published. The false positive cost
review time but did not broaden implementation scope.

**Revised solution:** v3 removes structural YAML-line inference. On the exact frozen base it constructs
the exact expected lockfile by replacing 31 known Next.js-family version occurrences and ten known npm
integrity values, then requires the real pnpm resolver result to byte-match it.

**Why chosen:** this is simpler, deterministic, auditable, and fail-closed for the exact frozen
implementation base.
